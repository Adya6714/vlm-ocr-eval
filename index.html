Abstract

Diagnosing Indic OCR: exposure, encoding, and confidence

Published Indic OCR scores mix two causes — how often a script was seen in training, and how hard it is to read — and they often count valid alternate Unicode spellings as errors. This project builds apparatus to separate those effects.

Design: a Stage 0 taxonomy; a HarfBuzz renderer with a glyph-frequency dial; a from-scratch instrument model; probes that ask whether confidence comes from reading or guessing. An API cannot answer Probes 2/3/5 — you need a model you own.

What actually ran is below the divider: Stages 0–1 measured in-tree; Hindi 2a reported from Colab; Bengali partial; Probe 6 / 5b / Stage 2b–6 out of scope or not run. See Status ledger.

Part One · The Idea

Does confidence come from reading — or from guessing?

A CER number cannot tell fluent language-prior guessing from genuine vision. Blank/noise controls, runner-up mass, and per-step confidence require opening the model — an API that returns text alone cannot answer Probes 2, 3, or 5. This project designs the apparatus to ask those questions on purpose.

The core idea
1. Method

Three pieces of apparatus — no run numbers required

Each piece exists because a CER table cannot answer one of the questions above.

Equivalence tiers

When two strings differ, is that a real misread — or the same reading in different bytes? Tier 1 encoding and Tier 2 phonetic equivalence keep alternate Unicode spellings from counting as OCR failure.

Exposure dial

When a language scores low, is it rarely seen or hard to see? Hold volume fixed and set glyph-cluster frequencies to natural / flattened / inverted — so exposure is a dial, not a corpus accident.

Confidence as target

When the model is sure, is it reading the image or guessing from language priors? Blank/noise controls and calibration buckets need per-step confidence and runner-up mass — which means owning the model.

SAY THIS

“Encoding-aware scoring, an exposure dial, an openable model. Everything else in the repo exists to land one of those three.”

Complete Bengali 3×3. One early Hindi signal (not a finding): inverted/seed2 showed 0% accuracy across every sampled confidence bucket (spread 0.3–0.9), unlike natural/seed0’s single-bucket overconfidence — exactly why the 9-run design exists.

What ran

What full scale would show

Whether synthetic findings hold on Tier C held-out pages with the same scorer — unknown until run.

Peak T4 VRAM under LoRA for SmolDocling-256M vs LightOnOCR-1B — the pick before any demo adapter training.

Future work
7. Future work

Designed on purpose — not abandoned

Each item has a reason it waits. Nothing here should be described as shipped.

DemoStage 2b

LoRA on a pretrained doc-VLM

Proves shipping shape (layout + reading-order modules). Must stay separate from the instrument — a pretrained backbone already has exposure history. Prerequisite: T4 VRAM benchmark script exists.

StructureStage 3

Reading order + table binding

Kendall tau vs layout complexity; cell↔header binding. Blocked on layout-bank gaps (form / table-embedded).

RLVR

Reward − coverage

Without a coverage penalty, a model raises accuracy by saying less. One planned ablation: remove coverage and quantify silence.

TransferStage 5

Does the finding rhyme at production scale?

~200 Sarvam pages, cached once; pre-specified rank correlation on Tier A and B. Null is still a finding.

CascadeStage 6

Router quality, not cost savings

Sweep escalation thresholds offline against the cache. Instrument is not expected to beat Tesseract on raw accuracy.

“Demo, structure metrics, transfer, cascade — designed, gated on time/T4, not because the instrument failed.”
