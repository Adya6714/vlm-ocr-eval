Abstract

A controlled OCR experiment

We’re building a controlled OCR experiment to separate data-exposure effects from intrinsic script difficulty, and then probing a model we own to understand whether its predictions, confidence, and errors are actually grounded in the visual input.

Stages 0–2a and the probe suite are the required path. Demo LoRA, structure metrics, transfer, and cascade are taught in BOOK.md but deferred this phase. Numbers recomputed in this checkout are measured; Colab write-ups without in-tree jsonl are reported.

Part One · The Idea · from BOOK.md

Not a product OCR — an experiment on why Indic OCR fails

Hard because it’s hard to see — or because it was rarely seen?

If an OCR model performs badly on a particular Indic character, is it because that character is inherently difficult to recognize, or simply because the model did not see it often enough during training? And when the model says it is 99% confident — is it actually looking at the image?

Chapter 0 · Why reading is hard
0. Background

A machine does not see letters; it sees numbers

A page is a grid of RGB values. Modern readers generate text one visual unit at a time from that grid. English clean-print OCR is mostly solved; Indic document OCR is not — for three tangled reasons.

Data

Training data is dominated by high-resource languages. A model can only get good at reading what it has seen enough of.

Script structure

Conjuncts, matras, and the shirorekha are a different geometric problem than Latin. One visual grapheme cluster can be many Unicode code points.

Causes tangle

A low language score could be exposure starvation, intrinsic difficulty, or both. A benchmark table alone cannot tell which — untangling requires controlling training exposure and owning the model.

That single sentence is the entire reason this project builds a model from scratch rather than only ever calling someone else’s API.

Chapter 1 · Measuring correctness
1. Evaluation

When two strings differ — is that a real misread?

Indic orthography allows many valid encodings. If you call those “errors,” every engine looks worse than it is. Stage 0 forces that answer into the open before anyone trains a new model.

Tier 1 — encoding

Deterministic, uncontroversial. Same reading, different bytes. Hand-curated tables in equivalence_tables.py.

Tier 2 — phonetic

A judgment call via ISO 15919 transliteration. Reported separately so arguable matches never inflate encoding noise.

Human residual

Genuine misread, dropped matra/nukta, order break, hallucination — or explicit no-fit. Alignment at grapheme clusters, not code points.

Chapter 3 · The instrument
3. Instrument

Learn to read from nothing — so “what did it see?” is answerable

Fine-tune a pretrained OCR/VLM and you still don’t know what caused its knowledge — it may already have seen millions of Indic pages. The instrument is ~19.5M parameters, grapheme-cluster vocabulary (not BPE), zero Indic pretraining, trained on line crops.

Chapter 7 · The probes
4. Probes

We built the model so we can open it up

Accuracy tells almost nothing about how the model arrived there. Think of the instrument as a patient in a lab, and the probes as medical tests. They are the project’s real deliverable.

1 · Exposure — does seeing more help?

Nine runs: natural / flattened / inverted × three seeds. Plot accuracy vs log exposure; residual after exposure is a candidate for intrinsic visual complexity.

2 · Confusion — what did it almost say?

Runner-up mass into a confusion graph. Closed APIs often return only the top string.

3 · Grounding — is it looking?

Real / blank / matched noise. Fluent high confidence on blank is language-prior guessing — more dangerous than an obvious failure.

4 · Fair scoring

Same Tier 1/2 rules on instrument outputs as on Tesseract.

5 · Calibration — can I trust confidence?

Especially on starved glyphs (Probe 1 × 5). Centerpiece practical question.

6 · Reality check

Do synthetic findings hold on Tier C real documents?
